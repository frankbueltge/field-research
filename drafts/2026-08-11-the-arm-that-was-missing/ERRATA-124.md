## E19 — a corrected number was still a typed literal, and it was wrong by the seventh day

**Where:** `FIGURES.md` §1, in every version through 0.3.1; the generator, `build_deliverable.py`.

**What was published:** *"On the balanced panel of units determinate on every day the spread is
**0.0577 pp**."* The figure was correct — for the **four-day** panel of version 0.1, on 3,465
units — and it was **typed into the generator as a literal**. It is the arc's own erratum E17
(session 121) and it was repaired the way E9 was: by typing the corrected number into an f-string.

**Why that is a defect and not a fix.** The balanced-panel spread is a property of the panel, and
the panel grows every measurement day. By the five-day panel the true figure is **0.0584 pp** on
3,423 units and the raw/balanced ratio is **2.32×**, not the 2.35× the page printed beside it. By
the six-day panel — the one this bundle now covers — it is **0.0886 pp** on 3,386 units and the
ratio is **1.53×**. A literal cannot track that; it is right on the day it is typed and drifts
every day after, which is the exact failure class (E6 of the first gauntlet, the reference clock)
this arc has already withdrawn a claim over.

**Repaired.** `FIGURES.md` is now generated by `figures_page.py`, which computes the balanced
panel from the series the bundle ships and fetches every figure from a named field
(`figures-derived.json:balanced_panel.range`). The registry entry `124-E19` fails the build if the
literal `0.0577` returns anywhere the correction is not also present.

**The equivalence this repair had to earn, tested rather than asserted**
(`routing-equivalence-124.json`): built on the same five-day panel version 0.3.1 shipped, the
routed page reproduces the old page's tables **figure for figure** in sections 1–5 (68, 48, 78, 10
and 12 numeric cells, all identical), and the four p-values match to the precision printed. Section
6 is the only table that differs, and it differs by **gaining a column on purpose** — the two
INDETERMINATE scopes the first gauntlet's finding 14 asked to be told apart. The two other former
literals, checked the same way: 248 of 249 control identifiers and 37 language editions both agree
with the values that had been typed, because those quantities happen not to change across these
panels — which is exactly why a literal that agrees today is not a fix.

## E20 — the double-probe accident was silently corrupting the bundle, not only costing requests

**Where:** `build_deliverable.py`, run discovery; surfaced by this session's first build.

**What was wrong.** Two complete probes ran over the same manifest on 2026-08-16
(`DOUBLE-PROBE-122.md`), and the record kept both, correctly. But the bundle builder discovered
each run as a separate **measurement day** keyed on its UTC date, so both carried the label
`2026-08-16`. The first build of this session produced a `MANIFEST.json` claiming **seven**
measurement days over six days of measurement, a `series` file carrying the label **twice**, and an
`expectation.json` whose cells for that day came from whichever of the two runs `os.walk` happened
to yield last. The doubled request load was the visible cost; a silently non-deterministic day of
the panel was the one nobody had named.

**Repaired.** A run file whose name carries `-second-probe` is recorded in the manifest as a
`replicate_runs` entry — visible, hashed, checkable — and is not a measurement day. Any duplicate
day-label that survives that rule is now a **hard build error**: the builder refuses rather than
picking one. The canonical run of 2026-08-16 is the one the record designates
(`run-2026-08-16T0337Z.json`); the second pass is named beside it and excluded from the series.

**This is the builder half of the accident.** The probe half — the lock that stops a second run
from starting at all — is `run_lock.py`, new this session, shown refusing on each shape of the
accident by `selftest_run_lock.py` (23 assertions, including six real processes racing through a
barrier). It closes the accident on this one filesystem by two mechanisms, both because a
reviewer of this session was right that a first, weaker version overclaimed: (1) the lock is
created with `O_CREAT | O_EXCL`, so of N probes starting the same manifest and day in the same
instant exactly one wins and the rest are refused — the earlier version's check-then-write could
have let both through; (2) a scheduled window run reserves the day *before* it holds to its hour,
in a process that survives the hold (`run_window_day.py`, wired into `run_day7.sh`), so a second
session opening during the hold sees a live lock and refuses. The 2026-08-16 accident needed both:
its two probes fired at the same second, and neither reserved during the hold. What the lock still
does **not** claim: to stop two probes launched from two separate checkouts of the repository,
which cannot see each other's lock. That limit is stated on the tool's own face. Session 122's
landing note wrote *"what is owed is a lock, not a note"* and did not build it; it is built here,
one session late, and the delay is in the record rather than absent from it.
