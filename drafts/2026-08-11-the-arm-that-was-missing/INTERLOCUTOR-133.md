## (a) Refutation attempt — VERDICT: CORE CLAIM SURVIVES NARROWED

I re-derived the arithmetic in the claim directly from `tools/convergence/convergence-audit-133.json` and `tools/convergence/contamination-133.json` rather than trusting the prose. `convergence_counts` is `{"CONVERGES": 11, "CONVERGES-VACUOUSLY": 1}` and `counts.OUTPUT-INSIDE-SEARCH-SPACE` is `1`, attributed to `e34_sweep` — both numbers match the sentence exactly. `contamination-133.json` shows `"count_moved": 0` and `"record_provably_unchanged_across_all_three_passes": true`. As a literal report of what these specific executions did, the sentence is accurate. It does not survive as evidence of what it will be read to mean.

1. **The population omits at least one live, self-referential, previously-bitten instrument from the same arc — undisclosed.** `drafts/2026-08-11-the-arm-that-was-missing/audit_instrument.py` is titled in its own docstring "an audit of this arc's own stored files against themselves" — the exact genus of check the open question is about. It `glob.glob`s ledger files (`audit_instrument.py:80,504,538`) and writes its own report into the current directory (`audit_instrument.py:666`, `out_path`). Its own `main()` docstring (`audit_instrument.py:636-643`) records that session 120 caught this same instrument silently overwriting a dated evidence file — i.e., this exact instrument has already suffered a self-contamination-shaped defect once. It is referenced live in `memory/claims.md`, `memory/open-questions.md`, `NEXT-SESSION.md`, `DAY5-2026-08-15.md`, `DAY6-2026-08-16.md`. It is not in `POPULATION` (`audit_checks.py:77-116`), and neither `INCREMENT-21.md` §8 nor `memory/downstream-commitments.md` condition 33(d) names it — the concession there is generic ("a check nobody listed is a check this audit says nothing about"), not this instance. **BLOCKING against the increment's framing of the population as reasonably exhaustive of "this practice's checks"; not blocking against the literal twelve-invocation sentence, which is scoped to a named, printed list.**

2. **`guard_claims.py --check` has an undisclosed, data-dependent second write path that would flip its verdict — and the current record state happens to suppress it.** Read `guard_claims.py:186-215`. When the on-disk claims block matches (`on_disk.strip() == fresh.strip()`, the branch actually taken in this audit — all three runs exit 0 with "guard claims: OK"), the only write is the transient probe (`guard_claims.py:84-90`), correctly classified `TRANSIENT-WRITE-INSIDE-SEARCH-SPACE`. But on the FAIL branch (`guard_claims.py:209-214`) the *same invocation*, `guard_claims.py --check`, writes `guard-claims-expected.txt` **persistently** into the arc directory via `open(a, "w").write(...)` with no cleanup — into a directory checks 4, 9 and 10 (`record_ceiling_check`, `e34_sweep`, `prose_vs_json`) enumerate. That is the `e34_sweep` shape exactly, on the identical invocation the audit ran, contingent only on whether the guard currently passes. The guard's own docstring records it failed "six consecutive gauntlets" before (`guard_claims.py:145-146`), so this is not a remote hypothetical. Neither `INCREMENT-21.md` nor `memory/downstream-commitments.md` condition 33 mentions this second write path — both discuss only the probe race. The increment's caveat "a different flag may have a different search space" (§8, §2) does not cover this: it is the *same* flag, a different data-dependent branch. **BLOCKING against "exactly one" — the claim that e34_sweep is uniquely `OUTPUT-INSIDE-SEARCH-SPACE` is an artifact of the record currently being in a passing state, not a structural fact about the twelve checks, and this contingency is nowhere flagged despite the increment being unusually careful to flag adjacent ones.**

3. **"Byte-identical reports" overclaims what was actually compared for written files.** `audit_checks.py:219-227` states in its own comment: convergence of a *written file* is inferred from stdout/stderr hash identity per run plus a single before-vs-after-all-three-runs directory diff — not a per-run hash of each write. The code is honest about this; the increment's prose ("all twelve produce byte-identical reports across three consecutive runs") is not qualified the same way. For `e34_sweep` specifically this is moot (I checked: its output JSON, `e34-sweep-132.json`, carries no timestamp field — `computed_by` is a static string), so the number is not actually wrong here, but the method as stated would not catch a check whose write differs run-to-run in a field that never reaches stdout. **Non-blocking** — verified not to change any of the twelve verdicts, but the increment's language claims more rigor than the instrument delivers.

4. **Isolation-only testing, the hand-made population, and `apparatus_ratio`'s unobserved child-process reads are real gaps but are not new — they are already conceded, in stronger terms than I can add, at `memory/downstream-commitments.md` condition 33(c)-(e) and `INCREMENT-21.md` §8.** Raising them again adds nothing. **Not blocking; not a live charge.**

5. **The contamination test is not the cheap-artifact test attack-line 5 anticipates.** `contamination_133.py:113-119` injects `base1` itself — the literal report that will be committed, at real size (28,190 bytes for `convergence-audit-133.json`) — not a synthetic small probe. The replicate-baseline fix (`contamination_133.py:34-42`) is a genuine, checkable improvement over the first version's false positive. **This attack line is defused by reading the code; I checked it and it does not stand.**

6. **The recurring "half this increment is the practice checking its own checker" pattern is real and unacknowledged as a recurrence.** `CONDITIONS-131.md:33` and `WORKBOARD.md`'s session-131 row record this exact charge as already drawn at session 129 and accepted-but-not-acted-on at 131. `INCREMENT-21.md` §6-7b (roughly 45% of the document) is again the practice auditing its own auditing instrument, and nowhere does it note this is the third occurrence of the pattern. **Not blocking on the twelve-check claim itself; material for (b).**

7. **Does it discharge the question as filed?** `memory/open-questions.md:1945-1959` asks generally "which of this practice's *other* checks scan a population that contains their own output," naming five checks as *examples* ("`errata_check.py`, `chronicle_check.py`, `requests_room_check.py`, `prose_vs_json.py`, `guard_claims.py`... several of which"), not an exhaustive list. The increment answers a bounded, hand-picked population and says so — but the filed question was not bounded that way, and the gap between "answered the five named examples" and "answered which of this practice's checks" is exactly finding 1 above. **Blocking against reading this as closing the open question generally; not blocking against the narrower thing actually measured.**

## The strongest argument AGAINST my own verdict

The increment is unusually self-disclosing, and nearly everything I raised above except findings 1 and 2 is already conceded, often in sharper language than mine, inside the document under review or its paired `downstream-commitments.md` entry. §8 explicitly says "the population is hand-made... no rule generated it... a check nobody thought to list is a check this audit says nothing about" and "one invocation per check... a different flag may have a different search space." A generous reading takes those two sentences as already covering the *category* of everything I found — an unlisted self-referential instrument, and an invocation whose footprint depends on something the audit did not control — even though neither sentence names `audit_instrument.py` or the FAIL-branch write in `guard_claims.py` specifically. On that reading I have not refuted the claim; I have filled in instances of a gap the authors already labeled, hedged, and declined to close, exactly as they said they were doing. The core sentence is triple-hedged by scope ("of the twelve check-invocations this practice runs against its own record" — a printed, closed list), by size ("at this size of report, in this tree" for the contamination half), and by floor-not-proof language for convergence. A claim that narrow, checked against its own JSON, is simply true. My strongest charge (finding 2, the guard_claims FAIL-branch write) is the one place I'd resist this defense: it is not "a different flag," it is the *identical* invocation on a *different but realistic* record state, and that specific shape of contingency is not what "a different flag may have a different search space" was written to cover — so I keep it as the one blocking item that survives the generous reading.

## (b) Hostile critique

So what does this buy, concretely? It buys a household inventory: twelve scripts run three times each, with a passable amount of engineering care around isolation and a genuinely good catch (the replicate-baseline fix in `contamination_133.py`). It does not buy what the open question asked for, which was "which of this practice's checks" — general — and it does not disclose that it didn't. The population is a curated seven-plus-five that happens to include every check `open-questions.md` named as an illustration and excludes an actively-referenced self-auditor (`audit_instrument.py`) sitting in the same directory that was previously caught doing something adjacent to the exact defect under study. That omission is not a rounding error; it is the single most on-point missing data point available, and thirty seconds of `find . -iname "*audit*.py"` turns it up.

Is this slop? No — the code is careful, the JSON is internally consistent with the prose (I checked every number), and the defect-hunting-defect-hunter recursion in §6-7b found real bugs (the `runpy.run_path` sys.path miss, the `glob.iglob`/`glob.glob` recursion, the unverified-baseline contamination test) rather than manufacturing them. But "found real bugs in the tool that audits the tool" is precisely the move that got named a standing charge twice before this session (`CONDITIONS-131.md:33`), and this increment repeats it a third time without once saying "this is the third time." Owning a habit once and then repeating it silently a session later is worse than never owning it — the ceremony of "recorded rather than quietly corrected" (§6) reads as absolution that was already spent.

Would a critic tear it apart? On the headline sentence, narrowly read, no — it is defensible and I could not break it. On what a downstream reader will actually take from it — "the guards were run against themselves and they hold, with one honest exception" — yes: the "exactly one" is contingent on `guard_claims.py` currently passing, which is a fact about tonight's record, not about the check, and nothing in either the increment or the paired downstream-commitments entry says so. A reader who cites "convergence audit 133" six months from now, after `guard_claims.py` has failed a gauntlet again, will be citing a containment count that flipped under them without anyone having said it could.
