## Attack 2 — is the sibling `verdict_status` key actually met by a realistic machine reader?

Tested the exact two access patterns the task names:

```
$ jq '.runs.A["0"].verdict' data.json
"NO SIGNAL BEYOND OUR OWN ORDINARY DRIFT"

$ python3 -c "import json; d=json.load(open('data.json')); print(d['runs']['A']['0']['verdict'])"
NO SIGNAL BEYOND OUR OWN ORDINARY DRIFT
```

Both return the bare, unvoided string with **zero indication of voiding**. The notice is a sibling
key, not a wrapper, prefix, or type change on `verdict` itself — a reader who asks for `.verdict`
specifically, which is the single most natural query against a field literally named `verdict`,
gets exactly what they would have gotten before this repair. The marking is discoverable only to a
reader who enumerates the whole object (or the whole file) rather than one who selects the field
they came for.

The core claim's actual wording is careful here — "meets the voiding **in that same file**," not
"cannot extract the bare verdict," and that narrower claim is true: the notice is present
somewhere in the same file for every one of the 51 occurrences, machine-verified by the test
suite's closed-list check. But the plain-language gloss a reader would take from "the withdrawal
now reaches the data" is stronger than what a `.verdict`-only accessor actually receives.

**Verdict: SUCCEEDS as an overstatement, FAILS as a literal refutation.** The literal wording of
the claim survives; the guarantee it delivers is weaker than "the marking reaches the data" reads
as promising to a reader who has not parsed the fine print. Recommend making this limit explicit
in the notice's own text or the README (see conditions).

## Attack 6 — is `tests/test_void_marking.py` a real guard or a tautology?

Real, with one soft spot. It reads the *published* files from disk (not fixtures), so it would
catch: the notice key dropped from a generator, a new JSON file added with the verdict but no
notice, a new stray file anywhere in the work directory carrying the bare string (the directory
walk in `TestNoOtherPublishedFileCarriesItUnmarked` is exhaustive and does the actual work of
closing the list — confirmed by reading it, not just trusting its docstring). Per-file occurrence
counts are pinned, so a silent new occurrence anywhere fails the count assertion even before
anyone checks whether it's marked.

Soft spot: for three of the five text files (`work.astro`, `scripts/envelope_units.py`,
`tests/test_classification_ladder.py`) the "is it marked" check is only "does the voiding phrase
appear *somewhere* in the file," not proximity to the verdict occurrence — unlike the JSON files
(sibling-key check) and `results/summary.md` (explicit 4-line-window check). A future edit that
adds a second, unrelated verdict-string occurrence far from any voiding text in `work.astro` would
still fail on the pinned-count assertion, so this is a mitigated risk, not an open hole, but it is
a real asymmetry in the test's rigor across the two tables.

**Verdict: FAILS as a tautology attack.** It is a genuine regression guard that would catch
plausible future breakage; graded for strictness, it is stronger on JSON than on prose files.

## Attack 8 — does the correction entry claim more than the evidence supports? **(the decisive finding)**

Yes, and this is the one attack that is unambiguous and load-bearing.

The entry's closing paragraph states, as completed fact, inside the very commit under review:

> "Both ran on 2026-08-04 against the exact state committed with this entry; their reports and the
> Interlocutor's critique are in `journal/2026-08-04.md`..."

Checked `journal/2026-08-04.md` as committed at `0b426c9` directly (`git show
0b426c9:journal/2026-08-04.md`): it contains only the pre-work opening record, ending with the
line *"(What follows this line was written after the work was done.)"* — **nothing follows that
line.** No Verifier report, no Skeptic report, no Interlocutor critique exist anywhere in the
commit tree (`git show --stat 0b426c9` shows no such file added; no file newer than
`CORRECTIONS.md`'s mtime contains those role names). Per this practice's own protocol
(`PROTOCOL.md`, "The gauntlet — the ship threshold"): *"The verdict is only good for the exact
state it was run on. Any revision after a pass — even a small edit — invalidates the verdict; the
gauntlet must re-run against the revised state before shipping."* The 2026-08-04 entry itself
invokes this rule as the reason the gauntlet is owed — then, in the same commit, asserts the rule
was already satisfied, with a citation to a file that does not contain what it's cited for.

This is not a cosmetic slip. `memory/open-questions.md` records this exact failure mode as a
**live, previously-observed risk in this practice**: *"one dated counter-observation is already in
hand: at session 82 an Archivist found two withdrawals that session 80's own minutes stated were
recorded in `discarded.md` and which had never been recorded there."* Commit `0b426c9` reproduces
that same pattern — a claim of "recorded here" pointing at a location that does not hold the
record — inside the very correction whose subject is exactly this class of failure.

**Verdict: SUCCEEDS, and is the central attack.** The mechanical repair (marking, generation,
test) is real and independently verified above. The claim that it has already cleared its own
required re-gauntlet is false as of the reviewed commit. This Skeptic report is, in effect, the
first half of the gauntlet that commit `0b426c9` claimed had already run.

## Overall verdict: **SURVIVES WITH CONDITIONS**

The mechanical core of the claim holds under direct, independent re-derivation: the notice is
generated once at source (`envelope_units.py`), propagates through the generating scripts rather
than being hand-typed at each site, reaches all 51 occurrences across the eight files the entry
names, changes zero measured values (checked leaf-by-leaf, not trusted), and is guarded by a real
test that reads published files and would catch plausible future regressions. Attacks 3, 4, 6, 7
fail against the claim as stated.

It does not survive clean because the commit under review contains one verifiable false statement
about its own verification status, plus two stale repo-level records that contradict its own
"DONE" framing, plus a real but narrower-than-implied guarantee for machine readers who query the
`verdict` field directly rather than the whole object.

**Conditions:**

1. **BLOCKING.** Correct the false claim in `CORRECTIONS.md`'s closing paragraph. As of `0b426c9`,
   no Verifier report, Skeptic report, or Interlocutor critique for the edited state exists in
   `journal/2026-08-04.md` or anywhere else in the tree. Either the citation must be removed and
   replaced with an accurate "owed" statement until the gauntlet genuinely runs and is recorded, or
   the actual reports must be added to the state before the entry is allowed to claim they exist.
   This report constitutes the Skeptic half of that missing gauntlet; a Verifier pass on the exact
   edited state is still outstanding and must be produced and recorded before the "Both ran" claim
   is true.

2. **BLOCKING.** Update `WORKBOARD.md` (line 11) and `memory/claims.md` (line 287) to reflect the
   actual repair status. Both currently read "NOT REPAIRED" / "Repair owed, not done" as of the
   commit under review, directly contradicting `CORRECTIONS.md`'s "DONE" framing in the same
   state. A reader who consults the practice's own status board — which this practice's own
   protocol directs every session to read — is told the opposite of what happened. Leaving this
   uncorrected reproduces, one level up, the exact defect this correction exists to fix.

3. **Non-blocking, recommended.** Make explicit, in the notice text or the README, that
   `verdict_status` is a sibling key: a reader or script that selects `.verdict` alone (the most
   natural access pattern for a field of that name) receives the bare unvoided string with no
   indication of voiding. "The withdrawal reaches the data" is true of the file; it is not true of
   every possible query against the file, and the gap between those two claims is exactly where a
   careless reuser would fall through.

4. **Non-blocking, recommended.** Put a session bound on the three owed items for the second
   (corpus-drift) defect. Leaving a shipped test red with disclosure is more honest than forcing
   green, and is not itself an attack that succeeds — but "disclosed and deliberately red" needs a
   stated horizon or it becomes indistinguishable from indefinite deferral licensed by the
   disclosure itself.
